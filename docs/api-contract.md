# Контракт API фронтенда

Контракт ведётся в [Apidog](https://app.apidog.com/project/1382426), в репозитории лежит его копия
`spec/openapi.json` и сгенерированное по ней:

- `apps/bff/src/go/client.ts` — fetch-клиент BFF к Go (Orval, мутатор `bearerFetch` в `apps/bff/src/go/fetch.ts`:
  адрес Go — обязательный `GO_API_URL` (в `bun run dev` по умолчанию Cloud Mock Apidog); `Authorization: Bearer` передаёт вызывающий код);
- `packages/schemas/src/zod.ts` — zod-схемы операций Go (Orval), пакет `@cdd/schemas`.

Клиент контракт Go не читает: он ходит только в BFF, типы процедур — `RouterInputs` / `RouterOutputs`
из `@cdd/bff` ([frontend#5](https://github.com/Cringe-Driven-Development-Team/frontend/issues/5)).

Все эти файлы коммитятся и руками не правятся: по диффу в PR видно, что поменялось в контракте Go

| Команда          | Что делает                                              |
| ---------------- | ------------------------------------------------------- |
| `bun run sync`   | всё сразу: выгрузка из Apidog и Orval                   |
| `bun run apidog` | выгружает спеку в `spec/openapi.json`                   |
| `bun run orval`  | генерирует клиент к Go и zod-схемы по `orval.config.ts` |

Для выгрузки нужен личный токен Apidog (`Account Settings` → `API Access Token`) в `.env`:

```sh
APIDOG_TOKEN=...
# ID sprint-ветки (серое число в Manage Sprint Branches). Пусто — ветка main
APIDOG_BRANCH_ID=
```

## Spec First и Cloud Mock

Работаем по Spec First: сначала согласованный контракт в Apidog, затем реализация
фронтенда, BFF и Go. Неготовность Go не мешает разработке по контракту и проверке
через Cloud Mock. Локальная `spec/openapi.json` и сгенерированные файлы могут отставать:
отсутствие в них операции не означает, что контракта ещё нет.

Перед задачей, затрагивающей Go API:

1. **Проверь актуальный Apidog.** По умолчанию используй main; другую ветку — если она
   задана задачей. При использовании MCP сначала обнови его данные, затем прочитай
   нужные операции и связанные схемы. Отсутствие MCP не блокирует работу: актуальная
   спецификация выгружается существующей командой `bun run sync`.
2. **Синхронизируй контракт и генерацию:** проверь `APIDOG_BRANCH_ID` (пусто — main)
   и выполни `bun run sync`. Проверь методы, пути, тела запросов, ответы, ошибки
   и описания операций в актуальном контракте. Если нужной операции нет и в Apidog,
   сначала согласуй контракт там. Не угадывай его по будущей реализации Go;
   спецификацию, клиент Go и zod-схемы руками не правь.
3. **Проверяй интерфейс через клиент → BFF → Cloud Mock Apidog.** `bun run dev`
   уже использует мок main. Для другой ветки возьми адрес её Cloud Mock в Apidog
   (проект → Mock → Cloud Mock) и задай `GO_API_URL`: контракт и мок должны быть
   из одной ветки. К адресу Cloud Mock не добавляй `/api/v1`.
4. **Если мок расходится с контрактом или не покрывает нужный сценарий, сначала
   доработай Cloud Mock отдельным MR в Apidog.** Исправь ответы и mock expectations
   по согласованному контракту; после слияния MR повтори проверку на Cloud Mock.
   Если нет доступа, сообщи, что именно мешает подготовить MR. Не обходи проблему
   собственным dev-сервером, имитирующим Go, ослаблением схем или ручной правкой
   сгенерированных файлов.
5. **Проверь сценарии задачи.** Проверь нужные задаче успешные ответы и ошибки. В отчёте укажи, что проверено на Cloud Mock,
   а что — на реальном Go.

Cloud Mock отвечает фиксированно и не доказывает сохранение изменений или отзыв
сессий в Go: состояние, сбои и таймауты проверяют на реальном Go после его готовности.
Подробнее о запуске — в [локальной разработке](local-development.md#bff).

## Локальный мок на Prism

Cloud Mock отвечает `412` (HTML прокси, не JSON мока) на `PATCH`/`DELETE`/`POST …/move`
ячеек с `If-Match`, который требует контракт: изменения ячеек через него руками не проверить.
Для этого есть `bun run dev:prism`: клиент и BFF как в `bun run dev`, а Go —
[Prism](https://github.com/stoplightio/prism) на `http://127.0.0.1:4010` по `spec/openapi.json`.
BFF получает `BFF_KEY=local-prism`, если ключ не задан: контракт требует `X-BFF-Key`, Prism
проверяет только его наличие.

- Ответы — **примеры контракта**. Своих мок-файлов нет: нужен другой пример — правь его в
  Apidog и выполни `bun run sync`. Prism проверяет запросы BFF по контракту (путь, тело,
  `If-Match`); статус отказа валидации зависит от нарушения и ответов операции
  в контракте (например, `400` или `422`).
- Только `cells.create` получает случайные данные (`Prefer: dynamic=true`), чтобы у новых
  ячеек были разные id; изредка короткий id может совпасть — тогда перезагрузите страницу.
- В консоли браузера `mock('cells.update', 409)` — следующий запрос с этой процедурой получит
  ответ мока с этим статусом, дальше снова успех. Работает для процедур с сессией (`cells.*`,
  `notebooks.*`, `users.*`); у `auth.*` правило снимается без эффекта. Клиент передаёт правило заголовком
  `X-Mock-Prefer`, BFF с `MOCK_PREFER=1` превращает его в `Prefer: code=…`. В обычном
  `bun run dev` и в production-сборке этого кода нет.
- Prism ничего не хранит: после перезагрузки блокнот снова из примера, а «серверная версия»
  при конфликте — тоже пример. Сохранение, конфликт с реальной версией, две вкладки,
  сеть и таймауты он не доказывает — это проверка на реальном Go.
