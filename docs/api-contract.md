# Контракт API фронтенда

Единственный редактируемый исходник контракта Go —
[`spec/openapi.json` в backend](https://github.com/Cringe-Driven-Development-Team/backend/blob/main/spec/openapi.json)
([процесс backend](https://github.com/Cringe-Driven-Development-Team/backend/blob/main/docs/openapi.md)).
В `spec/` здесь лежит его копия по полному Git SHA вместе с комплектом проверки backend:
`redocly.yaml`, плагин `plugins/defaults.js` и закрепление Redocly CLI (`package.json`,
`package-lock.json`). Ревизию фиксирует `spec/contract-source.json` (`repository`, `path`,
`revision`). По копии сгенерировано:

- `apps/bff/src/go/client.ts` — fetch-клиент BFF к Go (Orval, мутатор `bearerFetch` в `apps/bff/src/go/fetch.ts`:
  адрес Go — обязательный `GO_API_URL` (в `bun run dev` задаётся явно, умолчания нет); `Authorization: Bearer` передаёт вызывающий код);
- `packages/schemas/src/zod.ts` — zod-схемы операций Go (Orval), пакет `@cdd/schemas`.

Клиент контракт Go не читает: он ходит только в BFF, типы процедур — `RouterInputs` / `RouterOutputs`
из `@cdd/bff` ([frontend#5](https://github.com/Cringe-Driven-Development-Team/frontend/issues/5)).

Все эти файлы коммитятся и руками не правятся — ни копия `spec/`, ни generated-код: по диффу в PR
видно, что поменялось в контракте Go. Правка контракта — PR в backend; после его мержа копия
обновляется здесь по SHA.

| Команда                        | Что делает                                                                                                               |
| ------------------------------ | ------------------------------------------------------------------------------------------------------------------------ |
| `bun run contract:fetch <sha>` | скачивает комплект backend по полному SHA, проверяет его Redocly этой ревизии и только потом заменяет `spec/` и манифест |
| `bun run contract:tools`       | ставит Redocly CLI закреплённой версии в `spec/node_modules` (`npm ci`, нужен Node.js ≥ 22.12)                           |
| `bun run sync`                 | Redocly по закреплённой копии, затем Orval; ревизию не меняет, сеть не нужна                                             |
| `bun run orval`                | только Orval: клиент к Go и zod-схемы по `orval.config.ts`                                                               |
| `bun run contract:verify`      | сверяет `spec/` с backend по SHA из манифеста                                                                            |

Обновление контракта:

```sh
bun run contract:fetch <полный SHA коммита main backend>
bun run contract:tools   # после первого клонирования и при смене spec/package-lock.json
bun run sync
```

Ошибочный SHA, недоступный файл, сеть или ошибка Redocly — ненулевой код, прежние `spec/` и манифест
не меняются. CI (job `Check`) выполняет `contract:verify`, `contract:tools`, `bun run sync` и падает, если
`client.ts` или `zod.ts` отличаются от закоммиченных.

## Spec First

Работаем по Spec First: сначала согласованный контракт в backend, затем реализация
фронтенда, BFF и Go. Неготовность Go не мешает разработке по контракту. Локальная копия
и сгенерированные файлы могут отставать от main backend: отсутствие в них операции
не означает, что контракта ещё нет.

Перед задачей, затрагивающей Go API:

1. **Проверь актуальный контракт в backend** (`spec/openapi.json` в main или в ветке, заданной
   задачей). Если нужной операции нет, сначала согласуй её PR в backend. Не угадывай контракт
   по будущей реализации Go; копию, клиент Go и zod-схемы руками не правь.
2. **Обнови копию и генерацию:** `bun run contract:fetch <sha>` и `bun run sync`. Проверь
   методы, пути, тела запросов, ответы, ошибки и описания операций.
3. **Проверяй примеры и ошибки контракта через `bun run dev:prism`**, состояние — на реальном Go
   ([ниже](#реальный-go)). Если пример неудобен или неверен, правь его PR в backend; не обходи
   проблему собственным dev-сервером, имитирующим Go, ослаблением схем или ручной правкой
   сгенерированных файлов.
4. **Проверь сценарии задачи.** Проверь нужные задаче успешные ответы и ошибки. В отчёте укажи,
   что проверено на моке, а что — на реальном Go.

Prism отвечает примерами и не доказывает сохранение изменений или отзыв сессий в Go:
состояние, сбои и таймауты проверяют на реальном Go после его готовности.
Подробнее о запуске — в [локальной разработке](local-development.md#bff).

## Локальный мок на Prism

Проверка примеров и ошибок контракта без Go — `bun run dev:prism`: клиент и BFF как в `bun run dev`, а Go —
[Prism](https://github.com/stoplightio/prism) на `http://127.0.0.1:4010` по `spec/openapi.json`.
BFF получает `BFF_KEY=local-prism`, если ключ не задан: контракт требует `X-BFF-Key`, Prism
проверяет только его наличие.

- Ответы — **примеры контракта**. Своих мок-файлов нет: нужен другой пример — правь его PR в
  backend, затем `bun run contract:fetch <sha>` и `bun run sync`. Prism проверяет запросы BFF по контракту (путь, тело,
  `If-Match`); статус отказа валидации зависит от нарушения и ответов операции
  в контракте (например, `400` или `422`).
- Только `cells.create` получает случайные данные (`Prefer: dynamic=true`), чтобы у новых
  ячеек были разные id; изредка короткий id может совпасть — тогда перезагрузите страницу.
- В консоли браузера `mock('cells.update', 409)` — следующий запрос с этой процедурой получит
  ответ мока с этим статусом, дальше снова успех. Работает для процедур с сессией (`cells.*`,
  `notebooks.*`, `users.*`); у `auth.*` правило снимается без эффекта. Клиент передаёт правило заголовком
  `X-Mock-Prefer`, BFF с `MOCK_PREFER=1` превращает его в `Prefer: code=…`. В обычном
  `bun run dev` и в production-сборке этого кода нет.
- Prism ничего не хранит: после перезагрузки блокнот снова из примера, а «серверная версия»
  при конфликте — тоже пример. Сохранение, конфликт с реальной версией, две вкладки,
  сеть и таймауты он не доказывает — это проверка на реальном Go.

## Реальный Go

Интеграционная проверка состояния — сохранение, отзыв сессий, конфликты версий, сбои — идёт через
настоящий Go: `bun run dev` с явным `GO_API_URL`. Без него BFF не стартует и подсказывает, как задать
адрес или запустить Prism; внешние адреса сам не подставляет.

- `GO_API_URL` — адрес Go **с префиксом API**: `http://127.0.0.1:8080/api/v1`, а не корень сервера.
- `BFF_KEY` — S2S-ключ `X-BFF-Key`, если Go его проверяет (`BFF_API_KEY` на стороне Go). Без ключа
  такой Go отвечает `403` на все ручки. Значение — то же, что у выбранного Go.
- Обе переменные — в корневом `.env` (в git не попадает) или в окружении запуска.

Локальный Go в Docker не обязателен:

- **Свой Go.** `docker compose up -d` в checkout backend (README backend); адрес и ключ — из его `.env`.
  Нужную ревизию backend выбирай под задачу, обычно ту, что закреплена в `spec/contract-source.json`.
- **Удалённый backend команды.** Локальные клиент и BFF подключаются к разрешённому удалённому Go
  через доступ участника команды (SSH-туннель через gateway): маршрут, машины и требования к ключам —
  в [командном справочнике подключения](https://github.com/Cringe-Driven-Development-Team/agent-plugins-private/blob/main/plugins/cellestial-ops/skills/cellestial-ops/SKILL.md)
  (приватный репозиторий команды). `GO_API_URL` указывает на локальный конец туннеля с `/api/v1`,
  `BFF_KEY` берётся из хранилища секретов окружения. Сами адреса, ключи и реквизиты в документацию и
  `.env.example` не переносятся; к production без отдельного решения не подключаются.

В отчёте PR проверки на Prism и на реальном Go указываются отдельно, для Go — его ревизия и способ
подключения.
