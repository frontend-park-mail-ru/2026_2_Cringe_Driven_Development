# Spec First и Cloud Mock в инструкциях фронтенда

Дата: 2026-11-02. Статус: согласовано пользователем.

## Цель

Перед разработкой фронтенда и BFF агент проверяет актуальный контракт и Cloud Mock
в Apidog. Отсутствие реализации Go или операции в локальной копии спецификации
не становится поводом придумывать API и писать собственный сервер вместо Go.

## Подходы

1. Только AGENTS.md: компактно, но порядок работы для студентов остаётся разрозненным.
2. AGENTS.md и существующая документация: короткое обязательное правило для агента,
   подробный порядок в документации контракта и ссылка из локальной разработки.

Пользователь выбрал второй подход. Подробный порядок хранится в одном месте.

## Изменения

- `AGENTS.md`: перед задачами, затрагивающими Go API, обязательно читать
  `docs/api-contract.md`, проверять актуальный Apidog и использовать его Cloud Mock.
  При проблемах мока сначала отдельный MR в Apidog. Собственный dev-сервер,
  имитирующий Go, не создаётся для обхода неготового бэкенда или дефекта мока.
- `docs/api-contract.md`: описать Spec First, проверку контракта, синхронизацию,
  работу с Cloud Mock и порядок исправления расхождений.
- `docs/local-development.md`: рядом с описанием Cloud Mock дать ссылку на этот
  порядок. Существующие инструкции запуска и ограничения моков сохранить.

## Порядок работы

1. Прочитать документацию контракта и задачу. Проверить свежий контракт в Apidog,
   включая описания операций, тела запросов, ответы и ошибки. Локальная
   `spec/openapi.json` и сгенерированный код могут отставать от Apidog.
2. По умолчанию использовать main Apidog; другую ветку — когда она задана задачей.
   При использовании MCP обновлять его данные перед чтением; отсутствие MCP
   не отменяет существующий способ выгрузки через `bun run sync`.
3. Синхронизировать контракт и генерацию через `bun run sync`. Проверять
   `APIDOG_BRANCH_ID`: пустое значение означает main. Спецификацию, клиент Go
   и zod-схемы вручную не править. Если нужной операции нет и в актуальном Apidog,
   сначала согласовать её там, не угадывать контракт по будущей реализации Go.
4. Проверять интерфейс через клиент → BFF → Cloud Mock. У `bun run dev` уже
   задан мок main; при другой ветке `GO_API_URL` должен указывать на её Cloud Mock.
   Адрес мока берётся из Apidog, без добавления `/api/v1`.
5. Если Cloud Mock расходится с контрактом или не покрывает необходимый ответ,
   сначала доработать Cloud Mock отдельным MR в Apidog, после его слияния повторить
   проверку. При отсутствии доступа сообщить, что именно мешает подготовить MR.
   Не обходить проблему собственным сервером, ослаблением схем или ручной правкой
   сгенерированных файлов.
6. Проверять существующие сценарии командой `GO_API_URL=<Cloud Mock> bun run mock:check`
   и отдельно проверять сценарии своей задачи: текущая команда не покрывает всё API.
   В отчёте различать проверку на Cloud Mock и интеграцию с реальным Go.

## Ограничения и границы

- Доработка самих моков и PR #121 в эту правку документации не входят.
- Новые скрипты, зависимости и CI-проверки не нужны.
- Заглушки управляемых ответов в автоматических тестах сохраняются. Они проверяют
  в том числе сбои, таймауты и состояние, которое фиксированные ответы Cloud Mock
  не воспроизводят. Интеграцию с состоянием реального Go проверяют после его готовности.
- Неготовность Go не блокирует разработку по согласованному контракту и Cloud Mock;
  поддержку старого API ради порядка выкладки не добавляем.
- Подробный порядок и команды не дублируются во всех трёх файлах.

## Приёмка и проверка

Агент, прочитав AGENTS.md перед задачей наподобие frontend#41, получает явный маршрут:
актуальный Apidog → синхронизация → Cloud Mock → при дефекте отдельный MR в Apidog.
Он не делает вывод об отсутствии контракта только по локальной спецификации.
Изменения согласованы между тремя файлами, ссылки и команды соответствуют исходникам.
Перед завершением правки документации проходят `bun run check` и `bun run build`.

Расположение разделов и краткие формулировки остаются исполнителю; новые правила
и расширение этой области работ требуют отдельного обсуждения.
