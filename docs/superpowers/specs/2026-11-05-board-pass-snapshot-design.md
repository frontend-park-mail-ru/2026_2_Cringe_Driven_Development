# Один снимок релизов на проход Board

## Цель

Убрать повторные чтения истории внутри прохода синхронизации Scrumban, сохранив
полную сверку задач, восстановление пропущенных переходов и правило: успешная
выкатка учитывается после rollback, уже выкаченная задача не возвращается в ожидание.

Сейчас `reconcileBoard()` собирает снимок, а первый `refresh()` в `syncBoard()`
сразу собирает его повторно. Затем перед каждой подходящей задачей `refresh()`
читает все production deployments и отдельным запросом последний статус каждого.
Даже проверка совпадения текущего и целевого статуса выполняется после этих запросов.

## Рассмотренные подходы

1. **Один снимок на проход и проверка production в конце — выбран пользователем.**
   Если история изменилась во время обработки, следующий проход использует свежий
   снимок и заново проверяет все задачи, включая обработанные ранее.
2. **Один снимок на весь запуск без финальной проверки.** Проще, но обновление
   из параллельно завершившегося CD потребовало бы следующего запуска Board.
   Пользователь выбрал первый вариант.

## Поведение

- В начале прохода строится один полный снимок публикаций, выкаток, PR и связанных
  задач. Контрольное представление production относится к тем же данным, по которым
  построен снимок; отдельное начальное чтение только для его получения не нужно.
- Все карточки прохода обрабатываются по этому снимку. Внутри цикла задач нет
  повторного чтения каталога или истории production.
- Актуальное состояние issue и карточки по-прежнему читается перед решением об
  изменении. Перед записью сохраняется повторная проверка состояния issue, чтобы
  не перезаписать переоткрытие или изменение закрывающего PR.
- Сохраняются существующие проверки допустимости источника, Git-графа, публикации,
  образа, закрывающего PR и результата записи в Project, включая сброс устаревшего
  подтверждения того же статуса.
- После обработки всех карточек один раз читается актуальная история production
  вместе с последними статусами. Проверка обнаруживает как новые deployments, так
  и смену статуса уже существующего deployment.
- Если история совпадает со снимком, сверка заканчивается с учётом собранных ошибок.
  Если отличается, строится свежий снимок и выполняется следующий полный проход.
  Уже прочитанные в финальной проверке данные production можно использовать при
  построении следующего снимка; повторно получать их только ради пересчёта не нужно.
- Сохраняется предел в три прохода. Изменение истории на третьем проходе заканчивает
  запуск видимой ошибкой с предложением повторить Board, без ложного успеха.
- Во время прохода карточка может кратковременно отражать снимок до новой выкатки.
  Финальная проверка и следующий проход устраняют это расхождение. Изменение после
  финальной проверки обрабатывает следующий запуск workflow; атомарность с CD
  не заявляется.

## Область изменения

Координация в `scripts/release/sync.ts` и `board.ts`, передача снимка и контрольного
представления production в `catalog.ts`, связанные тесты и описание Board
в `docs/release.md`. Общий API чтения deployments менять только при необходимости
переиспользования уже полученных данных. Другие потребители каталога сохраняют
свои проверки и поведение.

Полная сверка истории остаётся. Кэш между запусками, отдельное хранилище,
обработка только события CI/CD, изменение очереди workflow, деплой приложения
и повторная отправка уведомлений в эту работу не входят.

## Проверка результата

- При неизменной истории каталог строится один раз; количество чтений истории
  production не растёт с числом карточек: чтение для снимка и финальная проверка.
- Новая успешная выкатка и смена `in_progress` на `success` в существующей записи
  во время прохода вызывают пересчёт; ранее обработанные карточки тоже получают Done.
- При постоянных изменениях истории выполняется не больше трёх проходов,
  затем возвращается явная ошибка.
- Сохраняются сценарии rollback, пропущенного обновления, переоткрытия issue,
  ручного закрытия, устаревшего подтверждения статуса и ошибок GitHub API.
- Проверяются тесты release-скриптов, `bun run check` и `bun run build`.
  Ускорение подтверждается числом запросов; конкретное время работы Actions
  заранее не обещается.

## Согласование

Подход выбран пользователем. Эта спецификация ожидает подтверждения перед
подготовкой плана реализации.
