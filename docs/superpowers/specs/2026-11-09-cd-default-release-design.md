# CD: последний опубликованный выпуск по умолчанию

Дата: 2026-11-09. Статус: поведение согласовано, включая уточнение выбора по истории main.

## Цель

Запускать ручной CD без копирования тега из Telegram или GitHub Releases.
При необходимости оператор по-прежнему выбирает конкретный выпуск тегом.

## Подходы

1. Выбор по истории `main` — согласованный вариант: самый новый коммит основной
   цепочки main, для которого есть опубликованный выпуск. Поздняя публикация
   старой сборки не вытесняет более свежий код.
2. Выбор по `published_at` — отклонён после обсуждения: старую сборку могут
   допубликовать позже новой, и время загрузки даст неверный порядок кода.
3. Выбор через GitHub `Latest` — отклонён: метку можно назначить другому выпуску,
   поэтому она не гарантирует выбор последнего опубликованного.

## Поведение

- Input `release` в `cd.yml` становится необязательным, без заданного тега по умолчанию.
  Подпись объясняет: пустое поле означает последний опубликованный выпуск.
- Непустое значение после удаления внешних пробелов — точный тег `release-<полный SHA>`;
  сохраняются текущая проверка формата и выбор конкретного Release.
- Пустое значение выбирает самый новый по истории `main` опубликованный Release
  с тегом `release-<полный SHA>`, исключая draft и prerelease. Учитываются все
  страницы API. Время публикации, даты коммитов, метка `Latest`, порядок ответа
  API и SHA запуска workflow не определяют выбор.
- Техническое решение: перед выбором обновляется локальная ссылка `origin/main`
  без переключения checkout. Зафиксированный main просматривается от вершины
  по `first-parent`, как в существующем `publicationBase`. Первый коммит с
  опубликованным Release — цель. Выпуски вне этой основной цепочки не выбираются.
- Выбор выполняется один раз в шаге `Ready release`, после получения очереди
  `release-board`. Выпуск, опубликованный во время ожидания CD в очереди, может
  стать выбранным. Дальнейшие шаги используют зафиксированные SHA, ID и digest.
- Выбранный выпуск проходит существующие проверки: immutable, точный SHA тега,
  manifest, происхождение сборки, состав и суммы артефактов; затем направление
  выкладки, доступность образа и CDN. Пересборки нет.
- Отсутствие кандидатов, ошибка чтения истории main или ошибка проверки выбранного
  выпуска останавливают CD до доступа к VPS. Автоматического перехода к более
  старому выпуску при ошибке нет.
- Лог шага сообщает выбранный тег и ссылку на Release при обоих способах выбора.

## Область изменения

Использовать существующие `listReleases`, `artifacts` и проверки в
`scripts/release/releases.ts`; обновить вызов CLI, если его проверка аргументов
не допускает пустое значение. Обновить `.github/workflows/cd.yml`, связанные
release/workflow-тесты и `docs/release.md`. Новые зависимости не нужны.

Rollback, публикация Releases, уведомления Telegram, очередь и правила
направления выкладки остаются прежними. Автоматический запуск CD не добавляется.

## Приёмка

1. Форма GitHub позволяет запустить CD с пустым `release`.
2. Для цепочки `A → B` выбирается B, даже если A опубликован позже и стоит
   первым в ответе API. Кандидат на следующей странице учитывается;
   draft/prerelease и выпуски вне основной цепочки main не участвуют.
3. Указанный тег выбирает именно этот выпуск, даже при наличии более нового.
4. Нет кандидатов или выбранный выпуск не проходит проверку — понятная ошибка,
   без доступа к VPS и без попытки выбрать старый выпуск.
5. Тег и ссылка видны в логах; остальные шаги получают SHA и артефакты выбранного
   Release. Существующие сценарии CD и Rollback проходят тесты.
6. `bun run check`, `bun run test`, `bun run build` проходят на ветке изменения.

Каждый выпуск — полная сборка коммита. Если B продолжает A, код изменений A
уже входит в B; отдельно выкатывать A не требуется. Архивы разных выпусков
между собой не объединяются.

Ручную выкатку на прод эта правка сама по себе не запускает.
